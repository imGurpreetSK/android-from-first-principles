## The problem

A network request on the main thread blocks the thread until the response comes. Then the OS cannot call `onDraw()`. The app freezes, and an Application Not Responding (ANR) dialog can show[^android-background-thread]. The [main thread chapter](/launch-path/main-thread/) shows the loop that the main thread runs.

The Android docs use coroutines for this problem. A suspend function can call `withContext(Dispatchers.IO)`. Then the request runs on an I/O thread, and the function is main-safe: a call from the main thread does not block the updates of the UI. A coroutine on the main thread calls the function and suspends until the `withContext` block ends. Then the coroutine continues on the main thread, with the result of the request[^android-main-safety].

Coroutines add two operations to call and return: suspend and resume. Suspend stops the current coroutine and saves all its local variables. Resume continues the coroutine from the place where it stopped[^adv-manage]. The `suspend` keyword does not move a function to a background thread. A suspend function can run on the main thread[^adv-main-safety].

Thus one function stops in the middle, and later the same function continues on the main thread, with its local variables. Kotlin implements each suspend function as a state machine, because a state machine needs no special support from the runtime[^spec-state-machine]. This chapter builds such a state machine by hand. Then it shows what the state machine alone does not do: send each resume back to the main thread.

## Build it naive

The rebuild is a coroutine written by hand, in plain Kotlin, in the module `samples/coroutines`. It does not use the `suspend` keyword or kotlinx.coroutines. Two fake loops act as the main thread and an I/O thread.

The compiler gives each suspend function an extra parameter, a continuation[^spec-continuation]. `Continuation<in T>` is the interface of a continuation after a suspension point. It has a context and the function `resumeWith`[^continuation-13]. `resumeWith` gives the result of the last suspension point to the coroutine, and the coroutine continues[^spec-continuation]. The rebuild has two loops: `main` for the UI and `io` for the network requests:

<Snippet file="coroutines/src/main/kotlin/NaiveContinuation.kt" region="loops" />

`fetchUser` is the suspension point. It posts the request to `io` and returns `SUSPENDED` at once. Later, the `io` loop calls `cont.resume` with the user:

<Snippet file="coroutines/src/main/kotlin/NaiveContinuation.kt" region="fetch" />

`LoadAndShow` is the state machine of the suspend function in its comment. The compiler splits a suspend function into steps. Each step, except the last step, ends with a suspending call. The field `label` holds the step that the next call of the state machine runs. Before the suspending call, the code sets `label` to the next step. If the call returns `COROUTINE_SUSPENDED`, the caller also returns `COROUTINE_SUSPENDED`. On resume, the state machine runs again, and `label` makes it jump to the next step[^codegen-state-machine].

Step 1 runs in a new call of `resume`, so it does not have the local variables of step 0. Thus, before a suspension point, the compiler saves the live local variables into fields of the continuation. After the resume, it reads them back. The codegen doc of the Kotlin compiler calls this "spilling"[^codegen-spilling]. The arguments of a suspend function are local variables, so the compiler spills them too[^codegen-parameters]. In the rebuild, the field `userId` holds the spilled argument:

<Snippet file="coroutines/src/main/kotlin/NaiveContinuation.kt" region="state-machine" />

`start` stores the argument and calls `resume(Unit)`. The library function `startCoroutine` also starts a coroutine with `resume(Unit)`[^continuation-112]. The first step of the state machine does not use this value[^codegen-startcoroutine].

A test drains `main`, `io` and `main` again. It checks that `show` gets `42` and the user. Thus the spilled `userId` lives across the suspension point:

## Where it breaks

The Kotlin spec says that in a typical UI app, the updates of the UI should run on a special UI thread[^spec-interception]. `show` is the UI step of `LoadAndShow`, so it must run on `main`. The breaking test records the loop of each call of `show`:

<Snippet file="coroutines/src/test/kotlin/NaiveContinuationTest.kt" region="flaw" />

1. The first drain of `main` runs step 0. `fetchUser` posts the request to `io` and returns `SUSPENDED`. Then `resume` returns, and `main` is free.
2. The drain of `io` runs the request. The request calls `resume` on `LoadAndShow` directly, so step 1 runs on `io`. Thus `show` runs on `io`.
3. The last drain of `main` runs no block.

The test passes, so the flaw occurs: the UI step runs on the loop of the callback, not on `main`.

The Kotlin standard library documents the same flaw. The intrinsic `suspendCoroutineUninterceptedOrReturn` gives a suspend function its continuation[^intrinsics-16]. A call of `resumeWith` on this continuation resumes the coroutine directly in the thread of the caller. The call does not go through the `ContinuationInterceptor` of the coroutine context[^intrinsics-29]. The Kotlin docs show this behavior with `Dispatchers.Unconfined`. After `delay(500)`, an unconfined coroutine continues on the thread `kotlinx.coroutines.DefaultExecutor`, the thread that `delay` uses[^docs-unconfined].

The state machine does not choose its thread. Some other part must move each resume to the correct loop.

## The real thing

### The compiler makes the state machine

The Kotlin spec describes the same transformation as the rebuild. Each suspend function gets an extra `Continuation` parameter, and its return type changes to `Any?`. The function returns its result, or `COROUTINE_SUSPENDED` if it suspends[^spec-cps]. The compiler makes each suspend lambda a continuation class. The class has fields for the local variables of the lambda and an integer field for the current step[^spec-state-machine].

The codegen doc gives the details of the JVM code:

- The state machine switches on `label`. Before each suspending call, it sets `label` to the next step. If the call returns `COROUTINE_SUSPENDED`, the function also returns `COROUTINE_SUSPENDED`. Each suspend function in the call stack returns, up to the coroutine builder[^codegen-state-machine].
- At run time, the return type is `Any?` (`java.lang.Object`), because the function returns its result or the marker[^codegen-cps].
- Before a suspension point, the compiler spills the live local variables into fields. After the resume, it reads them back. It does not spill the dead variables. It writes `null` into the field of a reference that is not necessary any more, so that the GC can collect the object[^codegen-spilling].
- A named suspend function keeps its state machine in the function itself. It keeps its state, `label` and the spilled variables, in a separate continuation object[^codegen-suspend-functions].

The Android docs say that a suspend copies the current stack frame and saves it for later[^adv-manage]. This is a simplification. The JVM code saves only the live local variables, in the fields of the continuation[^codegen-spilling].

<GoDeeper title="The JVM pass that makes the state machine">

`CoroutineTransformerMethodVisitor` is the JVM pass that finds the suspension points and makes the state machine[^codegen-suspend-markers]. At the start of the method, it adds a `tableswitch` on the `label` field of the continuation[^ctmv-323]. It names each field for a spilled variable with the first letter of the type descriptor, `$` and an index, for example `L$0` for a reference and `I$0` for an `int`[^ctmv-1578][^codegen-spilled-naming]. Before a suspension point, it can write `null` into a reference field `L$<index>`[^ctmv-1045].

</GoDeeper>

### `BaseContinuationImpl` runs the state machine

A resume of a compiled coroutine calls `BaseContinuationImpl.resumeWith`, and `resumeWith` calls `invokeSuspend`, which runs the state machine[^codegen-cps]. If `invokeSuspend` returns `COROUTINE_SUSPENDED`, `resumeWith` returns. If not, `resumeWith` gives the result to the completion, the continuation of the caller. If the completion is also a `BaseContinuationImpl`, the loop continues with the completion. Thus one resume continues each caller in turn, until a function suspends again or the top completion gets the result. A loop does this work, not a recursion[^continuationimpl-22][^codegen-cps].

### The interceptor chooses the thread

The rebuild needs a part between the callback and the state machine. In Kotlin, this part is the continuation interceptor. An interceptor intercepts the coroutine between suspension points. Usually, it wraps the continuation of the coroutine in another continuation. Thus an app can control where its code runs, for example on the UI thread[^spec-interception].

`ContinuationInterceptor` is an element of the coroutine context[^continuationinterceptor-20]. Its `interceptContinuation` returns a continuation that wraps the original continuation, and thus it intercepts all resumes. The framework keeps the result for each original continuation[^continuationinterceptor-27].

The function `intercepted()` does the wrap:

- The compiled state machine of a named suspend function or of a suspend lambda extends `ContinuationImpl`[^continuationimpl-98][^continuationimpl-156]. On a `ContinuationImpl`, `intercepted()` asks the interceptor of the context one time and keeps the result in a field[^continuationimpl-108].
- On each other continuation, `intercepted()` returns the continuation unchanged[^intrinsicsjvm-171].

The codegen doc shows an interceptor that resumes each continuation on a new thread. If the example does not call `intercepted()`, the coroutine stays on the thread that resumes it[^codegen-interception]. This is the flaw of the rebuild.

### Each suspension point resumes the intercepted continuation

A suspend function gets its own continuation from the intrinsic `suspendCoroutineUninterceptedOrReturn`. If the block of the intrinsic returns `COROUTINE_SUSPENDED`, the function suspends. Later, some code must resume the continuation[^intrinsics-16][^spec-intrinsics]. `suspendCoroutine` and `suspendCancellableCoroutine` intercept this continuation before they give it to their block:

- `suspendCoroutine` wraps `c.intercepted()` in a `SafeContinuation`[^continuation-142].
- `suspendCancellableCoroutine` wraps `uCont.intercepted()` in a `CancellableContinuationImpl`[^cancellablecontinuation-429]. Code uses this function to wait for the result of a single-shot callback API[^cancellablecontinuation-328].

Thus a callback does not resume the state machine directly. The resume goes through the wrapper of the interceptor.

The start of a coroutine also goes through the interceptor. `startCoroutine` calls `createCoroutineUnintercepted(completion).intercepted().resume(Unit)`[^continuation-112]. If code calls `resume(Unit)` on the unintercepted continuation, the coroutine starts at once in the call stack of the caller. If code calls `resume(Unit)` on the intercepted continuation, the coroutine and its completion run in the context that the interceptor sets[^intrinsicsjvm-108].

kotlinx.coroutines starts a coroutine in the same way. `launch` makes a `StandaloneCoroutine` as the completion and calls `coroutine.start`[^builders-200]. With the default start, `CoroutineStart.DEFAULT`, `start` calls `startCoroutineCancellable`[^abstractcoroutine-124][^coroutinestart-356]. `startCoroutineCancellable` creates the coroutine unintercepted, intercepts it, and resumes it with `Unit`[^cancellable-15].

<GoDeeper title="When a suspension point does not suspend">

The block of `suspendCoroutine` can call `resume` at once, in the same stack frame, before the suspend function returns[^continuation-132]. Then the function does not suspend. It returns the value, not `COROUTINE_SUSPENDED`[^intrinsics-16]. Each wrapper makes this decision with one atomic field:

- `SafeContinuation` starts as `UNDECIDED`. If `resumeWith` comes first, `SafeContinuation` stores the result. Then `getOrThrow` returns the value, and the function does not suspend. If `getOrThrow` comes first, it returns `COROUTINE_SUSPENDED`. Then a later `resumeWith` calls the wrapped continuation. A second resume throws "Already resumed"[^safecontinuation-35][^safecontinuation-50].
- `CancellableContinuationImpl` has the decisions `UNDECIDED`, `SUSPENDED` and `RESUMED`. The first call of `trySuspend` or `tryResume` wins[^cancellablecontinuationimpl-52]. `getResult` returns `COROUTINE_SUSPENDED` only if `trySuspend` wins[^cancellablecontinuationimpl-290]. If the resume comes first, the resume does not dispatch. If the resume comes later, it dispatches[^cancellablecontinuationimpl-467].

The codegen doc shows a resume inside the block of `suspendCoroutineUninterceptedOrReturn`, with no `SafeContinuation`. The result is undefined behavior. `SafeContinuation` prevents this problem[^codegen-safecontinuation].

</GoDeeper>

### `CoroutineDispatcher` posts the resume

In kotlinx.coroutines, the interceptor is the dispatcher. The dispatcher in the coroutine context decides which thread or threads run the coroutine[^docs-dispatchers]. All coroutines run in a dispatcher, also the coroutines on the main thread. The dispatcher resumes them[^adv-main-safety].

`CoroutineDispatcher` is a `ContinuationInterceptor`[^coroutinedispatcher-60]. Its `interceptContinuation` wraps each continuation in a `DispatchedContinuation`[^coroutinedispatcher-281]. `DispatchedContinuation.resumeWith` does not run the coroutine at once:

1. It calls `isDispatchNeeded` on the dispatcher.
2. If `isDispatchNeeded` returns true, it stores the result of the suspension point. Then it gives itself, as a `Runnable`, to `dispatch`[^dispatchedcontinuation-188]. `dispatch` can return before the `Runnable` runs[^coroutinedispatcher-41].
3. Later, a thread of the dispatcher calls `DispatchedTask.run`. `run` takes the stored result and calls `resume` on the wrapped continuation[^dispatchedtask-77]. Thus the state machine continues on the thread of the dispatcher.

If no dispatch is necessary, for example for `Dispatchers.Unconfined`, or for `Dispatchers.Main.immediate` on the main thread, the coroutine resumes on the current thread. An event loop prevents a stack overflow[^coroutinedispatcher-41][^dispatchedcontinuation-188].

### `Dispatchers.Main` posts to the main `Looper`

On Android, `Dispatchers.Main` is a `HandlerContext`. `AndroidDispatcherFactory` makes it around an asynchronous `Handler` of the main `Looper`[^handlerdispatcher-48]. `HandlerContext.dispatch` calls `handler.post(block)`[^handlerdispatcher-133]. Thus each resume on `Dispatchers.Main` is one message in the queue of the main `Looper`. The [main thread chapter](/launch-path/main-thread/) explains the queue and the asynchronous messages.

`HandlerContext.isDispatchNeeded` returns true, unless the dispatcher is `immediate` and the current `Looper` is the `Looper` of the `Handler`[^handlerdispatcher-129]. Thus `Dispatchers.Main` posts each resume, also a resume that comes from the main thread.

`HandlerContext` also implements `Delay`[^handlerdispatcher-110]. `delay` asks the `Delay` of the context to schedule the resume[^delay-121]. If the `ContinuationInterceptor` of the context implements `Delay`, it is the `Delay` of the context[^delay-149]. `HandlerContext.scheduleResumeAfterDelay` posts the resume with `handler.postDelayed`[^handlerdispatcher-139].

<GoDeeper title="How Dispatchers.Main finds HandlerContext">

`Dispatchers.Main` is a `@JvmStatic` property. Its value is `MainDispatcherLoader.dispatcher`[^dispatchers-18]. `MainDispatcherLoader` creates the dispatcher one time. If the system property `kotlinx.coroutines.fast.service.loader` is true, which is the default, it gets the factories from `FastServiceLoader`. If not, it uses `ServiceLoader`. Then it uses the factory with the highest `loadPriority`[^maindispatchers-13].

`FastServiceLoader` detects Android if the class `android.os.Build` is present[^fastserviceloader-13]. On Android, it creates `kotlinx.coroutines.android.AndroidDispatcherFactory` by its class name. It adds `TestMainDispatcherFactory` only if that class is present[^fastserviceloader-48]. `AndroidDispatcherFactory` creates a `HandlerContext` around `Looper.getMainLooper()`[^handlerdispatcher-48]. On API level 28 and higher, it makes the asynchronous `Handler` with `Handler.createAsync`, through reflection[^handlerdispatcher-80].

The main dispatcher prints its name as `Dispatchers.Main`[^handlerdispatcher-163][^maincoroutinedispatcher-64]. Prompt 3 of "Try it" shows this name.

</GoDeeper>

### `withContext` goes back to the dispatcher of the caller

`withContext` gets the continuation of its caller, `uCont`. If the new context has a new dispatcher, `withContext` makes a `DispatchedCoroutine`. It starts the block on the new dispatcher with `startCoroutineCancellable`[^builders-472]. Then it returns `getResult()`: `COROUTINE_SUSPENDED`, or the value if the block already ended[^builders-591]. When the block ends, `afterResume` resumes the caller through `uCont.intercepted()`[^builders-585]. The interceptor of `uCont` is the dispatcher of the caller. Thus the caller goes back to its own dispatcher, for example `Dispatchers.Main`. This is how `withContext(Dispatchers.IO)` makes a suspend function main-safe[^android-main-safety].
