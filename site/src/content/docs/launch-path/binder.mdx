## The problem

The [Zygote chapter](/launch-path/zygote/) ends in `ActivityThread.main`, in the new process of the launch app. `main` makes an `ActivityThread` and attaches it. Then it starts the loop of the main thread[^activitythread-9507]. To attach, `ActivityThread` gets the activity manager from `ActivityManager.getService()` and calls `attachApplication(mAppThread, startSeq)`[^activitythread-9282].

The app and `system_server` are two processes. On Android, one process cannot usually read the memory of another process[^aidl-intro]. Thus the app cannot give `system_server` a pointer to `mAppThread`. But `system_server` must call `mAppThread` later, for example with `bindApplication`[^ams-5451]. When the app calls `system_server` again, `system_server` must also find the record of the app.

Android uses Binder for this problem. With Binder, a process calls a method of an object in another process. For the caller, the call looks like a local call[^binder-overview]. A binder call is synchronous: `transact()` returns only after the target returns from `onTransact()`[^ibinder-39]. A binder object also keeps its identity across processes. If a process sends an `IBinder` to a second process, and the second process sends the same `IBinder` back, the first process gets the same object back. Thus a binder object can be a unique token across processes[^ibinder-50].

This chapter builds a binder in plain Kotlin that does not keep this identity. Its breaking tests show what then fails in the launch path. Then the chapter follows the real `attachApplication` call from the app into `system_server`.

## Build it naive

The rebuild is in the module `samples/binder`. It has no threads and no real processes. A `Process` object stands for one process. A `NaiveDriver` object stands for the binder driver in the kernel. Two processes share objects only through the driver.

The rebuild has two kinds of `IBinder`:

<Snippet file="binder/src/main/kotlin/Binder.kt" region="binder" />

- A `Binder` is a local object. Its `transact` calls its own `onTransact`. The real `Binder` is the local implementation of `IBinder`. Usually the AIDL tool generates its subclass[^binder-java-49].
- A `BinderProxy` stands for an object in another process. It holds a process and a handle: a number that the driver gave to that process. Its `transact` sends the call through the driver. The real `BinderProxy` is the Java proxy for a native `IBinder` object[^binderproxy-48].

A `Parcel` holds the arguments of a call. It keeps plain values and binders in the order of the writes:

<Snippet file="binder/src/main/kotlin/Binder.kt" region="parcel" />

The real `Parcel` holds flattened data and references to live `IBinder` objects. For a reference, the other side gets a proxy that is connected to the original `IBinder`[^parcel-90].

A process gets a handle only from the driver. For each handle, `proxyFor` makes a `BinderProxy`:

<Snippet file="binder/src/main/kotlin/NaiveDriver.kt" region="process" />

The driver keeps a handle table for each process. A handle is an index in the table of one process. `send` moves one binder from one process to another process:

<Snippet file="binder/src/main/kotlin/NaiveDriver.kt" region="send" />

- If the binder is a local `Binder`, the driver records `from` as its owner.
- If the binder is a `BinderProxy`, the driver finds the local object in the table of `from`.
- Then the driver adds the local object to the table of `to`, and `to` makes a proxy for the new handle.

`transact` sends one call. The driver finds the target object from the handle, in the table of the caller. It finds the owner of the target, copies the parcel into the owner, calls the target and copies the reply back. A copy keeps each value as it is. It sends each binder through `send`, so the receiver gets a handle in its own table:

<Snippet file="binder/src/main/kotlin/NaiveDriver.kt" region="transact" />

App code does not call `transact` directly. From an `.aidl` file, the build tools generate a Java interface with an inner `Stub` class that extends `Binder`[^aidl-defining]. The rebuild has this code, written by hand, for `IActivityManager` with one method, `attachApplication`:

<Snippet file="binder/src/main/kotlin/Aidl.kt" region="aidl" />

- `Stub` is the local side. It extends `Binder`, and its `asBinder()` returns the object itself. Its `onTransact` reads the arguments in the order of the writes and calls the method.
- `Proxy` is the remote side. It wraps a binder proxy, and its `asBinder()` returns that binder proxy. Its method writes the arguments into a `Parcel` and calls `transact` with the transaction code of the method.
- If the binder is a local object of the interface, `asInterface` returns the object itself. Otherwise, it returns a new `Proxy`.

`IApplicationThread` has the same shape, with no methods. `AppThread` is its stub: the binder object of the app.

The server of the rebuild stands for `ActivityManagerService` in `system_server`:

## Where it breaks

`send` gives `to` a new handle each time that a binder crosses. It does not look for a handle that `to` already has for the object. It also gives a handle to the owner of the object. And `proxyFor` makes a new `BinderProxy` for each handle. Thus the same object can reach a process as two different proxies.

The first breaking test sends `appThread` to the server two times. The first time is `attachApplication`. The second time is a direct `send`, the step that `transact` does for each binder in a parcel:

<Snippet file="binder/src/test/kotlin/NaiveDriverTest.kt" region="identity" />

The test passes, so the flaw occurs. The server has two `BinderProxy` objects for one `AppThread`. `recordFor` compares `asBinder()` by identity, so it finds no record for the second proxy. The real `ActivityManagerService` finds a `ProcessRecord` in the same way: it compares `asBinder()` with `==`[^processlist-4351][^ams-3978]. With this flaw, a lookup with a second proxy of the same app thread finds no record.

The second breaking test sends the thread of the record back to the app, the owner of `appThread`:

<Snippet file="binder/src/test/kotlin/NaiveDriverTest.kt" region="back" />

The test passes. The app gets a new `Proxy`, not its own `AppThread`. The real `IBinder` gives the opposite result: the original process gets the same `IBinder` object back[^ibinder-50].

The tests use one thread, no clock and no sleep, so they give the same result on each run.

## The real thing

### system_server publishes the activity manager

servicemanager keeps a map from service names to binders[^servicemanager-cpp-583]. At boot, servicemanager opens `/dev/binder`, adds itself as the service `manager` and becomes the context manager of the driver[^sm-main-153].

In `startBootstrapServices`, `system_server` calls `setSystemProcess`[^systemserver-1416]. `setSystemProcess` adds `ActivityManagerService` to servicemanager with the name `Context.ACTIVITY_SERVICE`[^ams-2127].

The app finds the service by this name. `ActivityManager.getService()` gets the `IBinder` of `Context.ACTIVITY_SERVICE` from `ServiceManager`, and wraps it with `IActivityManager.Stub.asInterface`[^activitymanager-6105]. `ServiceManager.getService` looks in a cache of the process first. If the cache has no entry for the name, it asks servicemanager[^servicemanager-java-150]. `ServiceManager` reaches servicemanager through the context object[^servicemanager-java-130]. The JNI method gets the context object from libbinder[^android-util-binder-1434]. libbinder gives the proxy for handle 0 as the context object[^processstate-183]. The rebuild has no servicemanager. Its test gives the app the first binder with `send`.

<GoDeeper title="servicemanager">

servicemanager refuses `addService` from an app UID[^servicemanager-cpp-512]. Before it adds or finds a service, it does an access check. If the check fails, servicemanager returns the error "SELinux denied for service."[^servicemanager-cpp-1134] In each process, the driver keeps the handle 0 for the context manager[^binder-c-1259].

Since Android 11, servicemanager uses libbinder: `ProcessState` and `IPCThreadState`. It adds itself as the service `manager`[^sm-main-11-121].

</GoDeeper>

### AIDL generates the Stub and the Proxy

`IActivityManager.aidl` declares `void attachApplication(in IApplicationThread app, long startSeq)`[^iactivitymanager-209]. The method is not `oneway`, so it is synchronous[^binder-threading-indicate]. `IApplicationThread.aidl` declares the whole interface `oneway`[^iapplicationthread-72]. A `oneway` call does not wait: the thread of the caller continues when the kernel has the transaction[^binder-threading-asynch]. Thus `system_server` does not wait for the app when it calls `bindApplication`.

The AIDL compiler makes this Java code from an `.aidl` file:

- A `Stub` class that extends `android.os.Binder`. Its `asBinder()` returns `this`[^aidl-gen-126].
- A transaction code for each method, `TRANSACTION_<method>`: `FIRST_CALL_TRANSACTION` plus an index[^aidl-gen-878]. `FIRST_CALL_TRANSACTION` is 1[^ibinder-100].
- A `Stub.Proxy` class with the field `mRemote`. Its `asBinder()` returns `mRemote`[^aidl-gen-368]. Each method of the proxy writes the interface token and the arguments into a `Parcel`. Then it calls `mRemote.transact` with the transaction code. For a `oneway` method, it adds `FLAG_ONEWAY`[^aidl-gen-772].
- The method `asInterface`. For null, it returns null. If `queryLocalInterface` gives a local object of the interface, it returns that object. Otherwise, it returns a new `Stub.Proxy`[^aidl-gen-319].

The rebuild has the same shape. Its `TRANSACTION_attachApplication` is 1. In the app, `ApplicationThread` extends `IApplicationThread.Stub`[^activitythread-1202].

### One call crosses

The binder overview calls the endpoint in the called process a node. It gives the steps of one call[^binder-overview]:

1. The client calls the proxy. The proxy makes a transaction with an identifier for the node, an identifier for the method and a copy of the arguments.
2. The binder driver in the kernel finds the process of the node. It copies the transaction into the address space of that process.
3. The driver gives the transaction to a thread in that process. The thread finds the node and calls the method.
4. The reply goes back through the driver to the proxy.

In libbinder, `IPCThreadState::transact` writes a `BC_TRANSACTION` command for the handle. If the call is not `oneway`, it waits for the reply[^ipcthreadstate-941]. It talks to the driver with the `BINDER_WRITE_READ` ioctl[^ipcthreadstate-1304]. While the thread waits for the reply, it runs each other command that the driver sends[^ipcthreadstate-1228].

For each transaction, the driver gives the receiver the effective UID and the PID of the sender[^binder-c-5312]. The thread that gets the transaction keeps them as the UID and the PID of the caller[^ipcthreadstate-1529]. Then JNI calls `Binder.execTransact`[^android-util-binder-431], which calls `onTransact`[^binder-java-1302].

`attachApplication` in `ActivityManagerService` reads the PID and the UID of the caller with `Binder.getCallingPid()` and `Binder.getCallingUid()`[^ams-5550]. `attachApplicationLocked` finds the `ProcessRecord` by the PID. If the start UID or the `startSeq` of that record is different from the call, it does not use that record[^ams-5201]. The doc of `getCallingPid` says not to use the PID as a security identifier, because the system can use a PID again. A `oneway` transaction gets no PID[^binder-java-307].

Then `attachApplicationLocked` does these steps:

1. It links to the death of the binder of the app, with an `AppDeathRecipient`[^ams-5283]. `linkToDeath` registers a recipient that the system calls when the process of the binder goes away[^ibinder-80].
2. It calls `thread.bindApplication`[^ams-5451].
3. It keeps the thread in the `ProcessRecord`, in an `ApplicationThreadDeferred` wrapper[^ams-5501]. The field `mThread` of `ProcessRecord` holds this wrapper[^processrecord-161].

In the app, `bindApplication` fills the service cache of `ServiceManager`[^activitythread-1482]. `initServiceCache` throws an exception if the cache is not empty[^servicemanager-java-361]. Then `bindApplication` sends the message `H.BIND_APPLICATION`[^activitythread-1543]. After `Application.onCreate`[^activitythread-8307], the app calls `finishAttachApplication` on the activity manager[^activitythread-8359].

Since Android 14, `IActivityManager` has the synchronous method `finishAttachApplication`[^iactivitymanager-14-199].

### The driver and each process keep the identity

This is the real fix for the flaw of the rebuild. One part is in the kernel driver. The other part is in each process.

When libbinder writes a binder into a `Parcel`, it writes a local object as `BINDER_TYPE_BINDER`, and a `BpBinder` as `BINDER_TYPE_HANDLE` with its handle[^parcel-cpp-291]. The driver keeps a node for each local object that a process sends, and a ref for each handle. A ref connects a handle of one process to a node.

When a transaction carries a local object, `binder_translate_binder` finds or makes the node of the object. It calls `binder_inc_ref_for_node` for the target process, and puts the handle of that ref into the transaction[^binder-c-2426]. `binder_inc_ref_for_node` makes a new ref only if the target process has no ref for the node[^binder-c-1646]. Thus one node has one handle in each process. The rebuild makes a new handle each time that a binder crosses.

When a transaction carries a handle, `binder_translate_handle` finds the node of the handle. If the node is in the target process, the driver puts the original local object into the transaction, not a handle[^binder-c-2479]. Otherwise, it puts the handle of the target process for the node[^binder-c-2526]. The rebuild gives the owner a new handle.

In each process, libbinder reads each binder from a `Parcel` with `unflattenBinder`. For a local object (`BINDER_TYPE_BINDER`), it gives back the original object. For a handle (`BINDER_TYPE_HANDLE`), it calls `getStrongProxyForHandle`[^parcel-cpp-466]. `getStrongProxyForHandle` makes a new `BpBinder` only if the handle has no live `BpBinder`[^processstate-339]. In Java, `javaObjectForIBinder` returns the original Java object for a local Java binder. For a remote object, it calls `BinderProxy.getInstance`[^android-util-binder-1010]. `getInstance` returns the same `BinderProxy` for the same native `IBinder`, while that `BinderProxy` is in use[^binderproxy-464]. Thus a process has one `BinderProxy` for each remote object. The rebuild makes a new proxy for each handle.

`ActivityManagerService` depends on this identity. `getRecordForAppLOSP` calls `ProcessList.getLRURecordForAppLOSP`, which compares `t.asBinder() == threadBinder` for each record in the LRU list[^processlist-4351]. If that call finds no record, `getRecordForAppLOSP` checks each `ProcessRecord` with `procThread.asBinder() == threadBinder`[^ams-3978]. The record keeps an `ApplicationThreadDeferred`. Its `asBinder()` returns the binder of the wrapped thread[^applicationthreaddeferred-96]. Thus the comparison uses the `BinderProxy` of the app.

<GoDeeper title="the binder driver">

The arm64 GKI kernel builds the C binder driver into the kernel. It builds the Rust binder driver only as a module. It also builds binderfs into the kernel[^gki-defconfig-674]. Thus this chapter cites `binder.c`. init mounts binderfs at `/dev/binderfs`, and makes `/dev/binder` a symlink to `/dev/binderfs/binder`[^init-rc-231].

Since Android 11, init mounts binderfs at `/dev/binderfs` and makes `/dev/binder` a symlink to `/dev/binderfs/binder`[^init-rc-11-175].

For a nested call, the driver looks at the transaction stack of the thread that calls. If a thread of the target process waits in that stack, the driver sends the transaction to that thread[^binder-c-3505].

</GoDeeper>

### The binder threads

The code of the launch app starts no thread, but its process has binder threads. `ZygoteInit.zygoteInit` calls `nativeZygoteInit` before `RuntimeInit.applicationInit`[^zygoteinit-983]. The JNI method calls `onZygoteInit` of the runtime[^androidruntime-284]. In an app process, `AppRuntime::onZygoteInit` calls `ProcessState::startThreadPool`[^app-main-92], which starts the first binder thread[^processstate-220]. A child zygote skips this step[^zygoteinit-998].

A process that hosts a node needs a pool of binder threads[^binder-threading]. When a transaction comes in, the kernel wakes a thread of the pool[^binder-threading-synch]. Thus a call from `system_server` to `ApplicationThread` runs on a binder thread of the app[^ibinder-61][^aidl-intro].

If no thread of the process waits for work, and the process has started fewer threads than its maximum, the driver sends `BR_SPAWN_LOOPER`[^binder-c-5421]. Then libbinder starts one more binder thread[^ipcthreadstate-1679]. The default maximum of libbinder is 15[^processstate-48][^binder-threading-configure]. `system_server` sets its maximum to 31[^systemserver-508][^systemserver-947].

libbinder gives each binder thread the name `<driver>:<pid>_<number>`. The number is in hex[^processstate-422] and starts at 1[^processstate-617]. Prompt 2 of "Try it" shows these threads.

Since Android 13, the name of a binder thread starts with the name of the driver, `binder`[^processstate-13-369].

If a thread waits for a reply, and the other process calls back into the process of the thread, the thread that waits runs the call[^ibinder-72][^binder-threading-nested].

<GoDeeper title="the transaction buffer">

The doc of `TransactionTooLargeException` says that the binder transaction buffer of a process has a fixed size, now 1 MB. All the transactions in progress for the process share it[^ttle-30]. libbinder maps a receive buffer of 1 MB minus two pages, read-only[^processstate-48][^processstate-624]. The driver limits the buffer of a process to 4 MB[^binder-alloc-925]. It gives `oneway` transactions only half of the buffer[^binder-alloc-951].

If a transaction fails and its parcel is larger than 200 KB, JNI throws `TransactionTooLargeException`. Otherwise, it throws `DeadObjectException`. The message says that the remote process probably died, or that the binder buffer is full[^android-util-binder-1146].

</GoDeeper>

<GoDeeper title="oneway calls and frozen apps">

The system runs the `oneway` calls to one `IBinder` one at a time, in the order of the calls[^ibinder-163].

The system can freeze a cached app. A frozen app gets no CPU time. If a process sends a synchronous call to a frozen process, the system kills the frozen process. A `oneway` call to a frozen process stays in a buffer until the system unfreezes the process[^binder-freezer-frozen-state][^ibinder-403]. In the driver, a synchronous call to a frozen process gets `BR_FROZEN_REPLY`[^binder-c-3042]. When `system_server` unfreezes a process, it reads the binder freeze info. If the process got a synchronous transaction while it was frozen, `system_server` kills it[^cachedappoptimizer-1477].

`IApplicationThread` is `oneway`, so a call from `system_server` to a frozen app does not kill the app. `ApplicationThreadDeferred` also holds back four calls while the process is paused (frozen). It runs them when the process is unpaused[^applicationthreaddeferred-33][^applicationthreaddeferred-46].

Since Android 12, the cached apps freezer is on by default[^cachedappoptimizer-12-104]. `system_server` freezes the binder of a cached app before it freezes the process[^cachedappoptimizer-12-1358].

Since Android 16, a process can register a `FrozenStateChangeCallback` on a remote binder[^ibinder-16-433].

</GoDeeper>
